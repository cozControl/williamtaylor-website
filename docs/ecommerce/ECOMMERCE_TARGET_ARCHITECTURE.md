# Ecommerce Target Architecture

## Direction

William Taylor is an ecommerce storefront. Existing Blade compositions remain code-owned; domain presenters feed them. Ordinary staff use **Edit -> Validate -> Save -> Live**. Immutable revisions and audit records may remain behind Save but must not impose candidate/projection/review terminology.

```text
Admin direct-save commands
        -> authorization + validation + transaction + audit/history
        -> domain models/read models
        -> exact storefront presenters
        -> existing Blade compositions
```

## Domain ownership

- **Global settings:** brand, announcement, navigation, contact, WhatsApp, social, footer and newsletter presentation.
- **Homepage:** fixed typed composition. Product, Collection and Campaign sections store ordered references, not copied cards.
- **Catalogue:** Product identity/lifecycle, immutable content history, Media roles, badges, Colour/Size options, Variants and SKU.
- **Collections:** identity/content, hero/card Media, ordered Product membership and visible/hidden state.
- **Campaigns:** Pre-Order and Limited Edition content, Products, Media and effective window. Only evidence-sensitive public claims retain specialized approval.
- **Pricing:** base Product price plus optional Variant override, currency and optional compare-at price, stored as integer minor units. One effective-price service feeds cards, Product pages, cart snapshots and Orders.
- **Inventory:** Variant/SKU-centric `InventoryItem`, `InventoryLocation`, immutable `StockMovement`, balance projection and Reservation. `available = on_hand - reserved`.
- **Cart/Checkout:** guest/customer Cart and Variant lines; server-resolved price snapshot; delivery/customer capture; inventory reservation; idempotent Order creation; payment boundary.
- **Customers:** separate from Admin staff. Guest or registered identity, addresses, Orders, receipts, wishlist, Gift Cards and communication preferences.
- **Orders:** evolve the existing aggregate; keep number, snapshots, minor-unit totals, status/payment history, notes, idempotency and lock version. Replace demo creation with checkout intake; retain `is_demo` only as internal migration/test classification until removable safely.
- **Communications:** transactional event outbox feeding Email/WhatsApp adapters and delivery history. Product work does not depend on it.
- **Gift Cards:** later stored-value liability with unguessable code/token, integer-minor balance and immutable redemption ledger.

## Existing foundation reuse

Product, ProductRevision, ProductOption/Value, ProductVariant, ProductBadge, Media Usage, Collection/Revision/Product membership, ProductPlacement, ProductRelation, Campaign/Revision/Product/Claim and Order history models are useful. Reuse their validation, archive safety, ordering fingerprints, locks and audit behavior. Add public read models and simple orchestration instead of a second catalogue.

## Product Media

Roles are primary, ordered gallery and optional Variant-specific media. Associations reference reusable ready Media Assets; removing an association never deletes the asset. Admin supports upload/select, thumbnail, alt text, primary selection, reorder and replace. Storefront URLs are generated by the Media provider. Variant Media is introduced only where Colour selection changes imagery.

ECOM-CATALOGUE-CORE-1 resolves Colour imagery at the Product Option Value level,
so one gallery is reused across every size Variant for that Colour. Hierarchical
Product Categories now own structural browsing and the primary breadcrumb;
Collections remain separate merchandising aggregates.

## Options and Variants

The current template proves Colour and Size. Keep the existing maximum-two-axis foundation for the first slice. Every active sellable combination has one unique SKU and position; default Variant is explicit. Fit remains Product descriptive content unless a current template proves it is a selectable axis. Variant price override and InventoryItem are separate later relationships.

## Merchandising

Named slots encode real template locations: Homepage New Arrivals, Homepage Featured Product, Homepage Collection Cards, Homepage Campaign Panels and ordered Related Products. Commands search/add/remove/reorder eligible references and save atomically. Frontend code never embeds Product IDs.

## Safety boundaries

Direct Save retains RBAC, server validation, transactions, unique SKU/slug constraints, optimistic locking, audit/history and archive rules. Monetary values use integer minor units. Stock changes use immutable movements and idempotency. Checkout never accepts client prices or availability as authoritative.
